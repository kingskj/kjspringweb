## 3. 설계 핑퐁 요약

### 딴지 1 — `entryMethodId` DB 컬럼 없음 (Claude 제기)

**쟁점**: `endpoint_mapping`에 `entry_method_id` 컬럼이 없음. `method_path`(`FQCN@methodName`)로 `method_def.fqcn_method`(`FQCN#methodName(paramTypes...)`)를 JOIN하는 방식은 구분자 다르고 파라미터 정보 없어서 불가.

**GPT 보정**: `method_path` 포맷 불일치 확인. 역조인 불가. 다만 `entry_method_id` 컬럼 추가도 불필요 — `method_mapping WHERE parent_method_id = 0`이 endpoint당 루트 진입 메서드를 보장함 (`MappingAssembler`가 명시적으로 삽입).

**최종 결론**: `endpoint_mapping` 스키마 변경 없이 `method_mapping.parent_method_id = 0`에서 `entryMethodId` 조립.

---

### 딴지 2 — `path` vs `entryKey` (Claude 제기)

**쟁점**: 지시문에서 `path`를 HTTP 전용으로 쓰고 비HTTP는 null로 처리하면, BATCH/SCHEDULE의 진입점 식별값이 agent에 안 내려감.

**확정**: `path` → `entryKey`로 변경. `entryKey`는 `endpoint_mapping.entry_key`를 그대로 내려주는 것 (새 컬럼 추가 아님).

**실제 값**:
- HTTP: URI (`/board/list`)
- SCHEDULE/INTERFACE: `fqcn@methodName` (`BatchJobExtractor` 기준)
- BATCH/KAFKA: 현재 미일반화

---

### 딴지 3 — `MethodMappingRepository` 조회 메서드 없음 (Claude 제기)

**쟁점**: `endpointMethods[]` 또는 `entryMethodId` 조립에 `method_mapping` 조회가 필요한데 해당 메서드 없음.

**확정**: `findRootPairsByCommitHash(commitHash)` 추가 필요.

---

### 딴지 4 — `ok()` 팩토리 시그니처 (Claude 제기)

`AgentMetaResponse`가 Java record라서 필드 추가 시 `ok()`/`logOff()` 팩토리도 함께 수정 필요. `logOff()`는 빈 리스트로 고정.

---

### `endpointMethods[]` 제외 결정

**배경**: 원래 지시문에 `endpointMethods[]`(endpoint-method 다대다 관계 배열)도 포함되어 있었음.

**논의 과정**:
- Claude: 7섹터 목적만 놓고 보면 `endpoints[].entryMethodId`만 있으면 agent가 루트 진입 시점에 context 시작 가능하고 이후 하위 메서드는 context 따라가면 됨. `endpointMethods[]` 없어도 귀속 가능.
- GPT: `endpointMethods[]`는 "정적 도달 가능 메서드 집합"이지 "런타임 실행 경로"가 아님. 분기/루프로 인해 if 안의 두 메서드가 모두 엔드포인트 소속으로 잡히는데, 실제 요청 1건에서는 하나만 실행됨. 런타임 경로 대용으로 쓰면 오해 소지.
- 오빠: `endpointMethods[]`는 엔진에서 서비스/UI 도식화 용도로 구현 대기 중인 것. 로그 기록 목적 아님. 개발 순서도 가장 마지막.

**확정**: `endpointMethods[]`는 이번 범위 제외. 후순위 도식화 기능으로 분리.

---

### 불변조건 위반 처리 방식

**논의**: 무결성 검증 위반 시 `LIMIT 1` 방어로 하나 고를지 vs 검증 후 fail로 처리할지.

**결론**: `LIMIT 1`은 이상 상태를 숨기므로 금지. endpoint당 root pair가 정확히 1개인 것이 invariant라서 2개 이상이면 `warn + LOG_OFF ENGINE_DATA_INTEGRITY_ERROR`로 처리.
