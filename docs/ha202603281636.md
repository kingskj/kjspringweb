## 3. 주요 설계 결정

### 3-1. ASM 번들 방식 (호스트 무간섭 원칙)

전 진입점(HTTP/Batch/Schedule/Kafka) 포괄을 위해 ASM 바이트코드 계측 필요.
호스트 프로젝트에 의존성 추가 불가 원칙 → shadow + relocate로 agent JAR 내부 번들.

- ASM 버전: `9.9.1` (`asm`, `asm-commons`)
- shadow plugin: `com.gradleup.shadow 9.3.2` (빌드 JDK Java 17+ 필요, 산출물은 Java 8)
- relocate: `org.objectweb.asm.*` → `com.turtlepick.agent.shaded.asm.*`
- **소스 import는 `org.objectweb.asm.*` 유지** — relocate는 빌드 산출물에서만 적용
- `jar { enabled = false }` 필수 — shadowJar와 regular jar 충돌 방지

### 3-2. build.gradle 확정안


## 4. 딴지 및 수용 내역 (핑퐁 전체)

### 딴지 1 — `loader == null` bootstrap classloader skip 누락

**Claude 제기**: `ApplicationMethodTransformer.transform()` 에서 `loader == null` 체크 없으면 JDK 클래스까지 transform 시도. JVM 불안정 초래 가능.

**수용**: `transform()` 맨 앞에 추가.
```java
if (loader == null) {
    return null;
}
```

---

### 딴지 2 — ASM import / relocate 방향

**Claude 제기**: `com.turtlepick.agent.shaded.asm.*` 를 소스에서 직접 import하면 컴파일 안 됨. relocate는 빌드 산출물에서만 적용.

**수용**: 소스 import는 `org.objectweb.asm.*` 유지, 산출물에서만 relocate.

---

### 딴지 3 — `appendToSystemClassLoaderSearch` → `addTransformer` 순서

**Claude 제기**: `addTransformer` 이후 transform된 클래스가 `RuntimeMethodBridge`를 찾으려면, 그 시점에 agent JAR가 system classloader에 검색 경로로 등록되어 있어야 함. 순서 역전 시 `NoClassDefFoundError`.

**수용**: `appendToSystemClassLoaderSearch(new JarFile(agentJarFile))` 를 bootstrap 로직 전 최상단으로 이동.

---

### 딴지 4 — `BRIDGE_OWNER` / descriptor 수기 문자열

**Claude 제기**: `MethodProbeAdviceAdapter`에서 `RuntimeMethodBridge` 호출 바이트코드 삽입 시 내부 이름/descriptor를 수기 문자열로 하드코딩하면 오타가 컴파일 에러 없이 런타임 `VerifyError`로 터짐.

**수용**: `Type.getInternalName(RuntimeMethodBridge.class)` / `Type.getMethodDescriptor(...)` 로 교체.
```java
private static final String BRIDGE_OWNER =
        Type.getInternalName(RuntimeMethodBridge.class);

private static final String ENTER_DESC =
        Type.getMethodDescriptor(Type.VOID_TYPE, Type.INT_TYPE, Type.getType(String.class));

private static final String EXIT_DESC =
        Type.getMethodDescriptor(Type.VOID_TYPE, Type.INT_TYPE, Type.BOOLEAN_TYPE);
```

---

### 딴지 5 — `RuntimeMethodBridge.exit()` stack mismatch 방어

**Claude 제기**: `onMethodExit`이 여러 exit point마다 호출되는 구조에서, Deque의 peek/pop이 idempotent하지 않으면 로그 중복 또는 stack 깨짐 발생. 특히 methodId 불일치 시 무처리로 두면 이후 모든 트레이스가 오염됨.

**수용**:
```java
if (top.getMethodId() != methodId) {
    AgentLog.warn("method stack mismatch expected=" + methodId + " actual=" + top.getMethodId());
    context.clear();
    TraceContextHolder.clear();
    return;
}
```
스택 비면 `TraceContextHolder.clear()` 호출하여 ThreadLocal 정리.

---

### 딴지 6 — `MethodProbeIndexBuilder` parse 실패 silent skip

**Claude 제기**: `MethodSignatureParser.parse()` 실패 시 catch 후 조용히 continue하면 어떤 메서드가 누락됐는지 알 수 없음.

**수용**: `AgentLog.warn()` + continue.
```java
} catch (RuntimeException e) {
    AgentLog.warn("method probe parse skipped fqcnMethod=" + entry.getKey() + " reason=" + e.getMessage());
}
```

---

### 딴지 7 — native 메서드 skip

**Claude 제기 (선제)**: `ApplicationClassVisitor.visitMethod()` 에서 native 메서드를 `AdviceAdapter`로 감싸면 즉시 오작동. native 메서드는 바이트코드 없음.

**수용**: `visitMethod()` 내 필터 추가.
```java
if ((access & Opcodes.ACC_NATIVE) != 0) {
    return methodVisitor;
}
if ((access & Opcodes.ACC_ABSTRACT) != 0) {
    return methodVisitor;
}
if ("<init>".equals(name) || "<clinit>".equals(name)) {
    return methodVisitor;
}
```

---

### 딴지 8 — `ClassWriter.COMPUTE_FRAMES` + `getCommonSuperClass()` 기본 구현 위험

**Claude 제기**: `ClassWriter.COMPUTE_FRAMES` 사용 시 ASM이 두 타입의 공통 조상을 찾기 위해 `getCommonSuperClass()` 호출. 기본 구현은 `Class.forName()` 기반 → javaagent transform 문맥에서 `ClassCircularityError`, `ClassNotFoundException`, `NullPointerException` 발생 가능.

**수용**: `ClassWriter` 서브클래스(`SafeClassWriter`)로 override.
```java
private static final class SafeClassWriter extends ClassWriter {

    private SafeClassWriter(ClassReader classReader) {
        super(classReader, ClassWriter.COMPUTE_FRAMES);
    }

    @Override
    protected String getCommonSuperClass(String type1, String type2) {
        if (type1 == null || type2 == null) {
            return "java/lang/Object";
        }
        if (type1.equals(type2)) {
            return type1;
        }
        return "java/lang/Object";
    }
}
```
`java/lang/Object` fallback은 frame 계산을 보수적으로 만들지만 VerifyError 발생을 크게 줄임. "절대 안전" 단정은 하지 않음 — 1차 범위에서 가장 안전한 기본안.

---

### 딴지 9 — `MethodProbeIndex.find()` ambiguous match `throw` 방향

**Claude 제기**: `transform()` → `reader.accept()` → `visitMethod()` → `find()` 체인에서 `IllegalStateException` throw 시 JVM이 조용히 삼킴 (transform() 예외 = null 반환 동일 처리). 로그 없이 계측 누락.

**수용**: `throw` → `AgentLog.warn() + return null`.
```java
if (matched != null) {
    AgentLog.warn("ambiguous method probe skip"
            + " className=" + className
            + " methodName=" + methodName);
    return null;
}
```

## 11. 서버 에이전트 사이클

서버 에이전트의 전체 동작 사이클은 두 단계로 구분된다.

### Phase 1 — Bootstrap (JVM 기동 시 1회)

```
JVM 시작
  └─ premain() 실행
       ├─ appendToSystemClassLoaderSearch(agentJar)   ← RuntimeMethodBridge 가시성 확보
       ├─ turtlepick.properties 로드
       ├─ git rev-parse HEAD → full commit hash 추출
       ├─ POST /api/agent/meta (commitHash, serverId)
       │     └─ 응답: OK + methods[]
       │           ├─ methodId
       │           └─ fqcnMethod (com.example.Foo#bar(int,String))
       ├─ MethodMappingRegistry 적재 (fqcnMethod → methodId)
       ├─ MethodProbeIndex 빌드 (className → List<MethodProbeSpec>)
       ├─ ApplicationMethodTransformer 등록
       └─ AgentState = LOG_ON
```

meta 응답이 OK가 아니면 AgentState = LOG_OFF 유지, transformer 등록 안 함 → 호스트 서버는 정상 기동.

### Phase 2 — Runtime (요청/배치/스케줄 처리 중, 반복)

```
클래스 로더가 대상 클래스 로드 시도
  └─ ApplicationMethodTransformer.transform() 호출
       ├─ loader == null → skip (bootstrap classloader)
       ├─ MethodProbeIndex.containsClass() → 비대상 → skip
       └─ 대상 클래스
            └─ ApplicationClassVisitor.visitMethod()
                 ├─ native / abstract / 생성자 → skip
                 └─ MethodProbeIndex.find(className, methodName, paramTypes) 매칭
                      └─ MethodProbeAdviceAdapter 삽입
                           ├─ onMethodEnter → RuntimeMethodBridge.enter(methodId, fqcnMethod)
                           └─ onMethodExit  → RuntimeMethodBridge.exit(methodId, isException)

─────────────────────────────────────────────────

HTTP 요청 / Batch Step / Schedule 실행 시
  └─ 진입점 메서드 enter
       └─ TraceContextHolder.getOrCreate()
            └─ RuntimeTraceContext 생성 (traceId = UUID)
                 └─ MethodFrame push (methodId, fqcnMethod, startNanoTime)

  내부 호출 메서드들 enter/exit 반복
       └─ Deque<MethodFrame> push/pop

  진입점 메서드 exit
       └─ Deque 비어짐 → TraceContextHolder.clear()
            └─ [7섹터] 로그 파일 기록
                 └─ [8~9섹터] log-ready 전송 → 엔진 수거
```

### Phase 3 — 엔진 수거 (비즉시성, 7~9섹터 이후)

```
엔진
  └─ POST /api/agent/log-ready 수신
       └─ 로그 파일 위치 파악 → 수거
            └─ 분석 처리 (MTTR 단축 목적)
```

> **비즉시성 원칙**: agent는 실시간 전송하지 않는다. 로그를 파일에 쌓고 엔진이 주기적으로 수거한다.
> 요청 처리 스레드 영향 최소화 목적.
