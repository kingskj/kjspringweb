# 2026-05-03 작업 일지 - 서버 agent trace 로그 정비 총괄

## 문서 성격

- 이 문서는 2026-05-03 하루 동안 진행한 서버 agent trace 로그 정비 작업의 총괄 일지다.
- 파일명 시각은 최초 작성 시각이며, 세션 단위 문서가 아니라 하루 작업 흐름을 복원하기 위한 기준 문서로 본다.
- Unit 6 에러 파라미터 캡처는 이 문서에는 요약만 남긴다.
- Unit 6 상세 구현 및 검증 기록은 별도 상세 문서 작성 대상이다. 현재 상세 맥락은 `gpt.md` 102~107번 기록에 남아 있다.

## 하루 결론

- 기존 trace 로그는 요청이 찍히는지만 확인 가능한 수준이었다.
- 2026-05-03 작업으로 서버 agent trace 로그는 최소한 아래 정보를 표현할 수 있게 됐다.
  - 파일 헤더: format version, commitHash, createdAt, verbose field mode
  - 요청 레코드: endpointId, error 여부, method call tree
  - 에러 레코드: errorCallId, exception/rootException, userFrames, errorArgs
- 정상/에러 요청 모두 파일 단위 NDJSON 구조로 append-safe 하게 유지한다.
- 서버 agent는 로그 원본을 암호화/마스킹하지 않는다. 난독화, 압축, 암호화는 엔진이 파일을 수거한 뒤 최종 저장 직전에 처리한다.

## 핵심 결정사항

- node 식별자는 `methodId`가 아니라 요청 내 호출 인스턴스인 `callId`다.
- 부모 관계는 `parentCallId`로 표현한다.
- `methodId`는 엔진 method registry를 역참조하기 위한 메서드 ID일 뿐이다.
- trace 파일은 전체 JSON object가 아니라 줄 단위 완결 JSON 레코드로 유지한다.
- 파일 첫 줄은 header record, 이후 줄은 trace record다.
- header key는 항상 short key로 고정한다.
- `vfn` 값으로 본문 레코드가 compact key인지 verbose key인지 판단한다.
- 에러 정보는 최초 예외 발생 지점 기준 first-write-wins로 저장한다.
- CGLIB proxy frame, lineNumber 음수 frame은 userFrames에서 제외한다.
- 에러 파라미터는 에러 경로에서만 캡처한다. 정상 요청 파라미터 캡처는 이번 범위가 아니다.

## Unit 1 - nodes[] call tree 적재

### 왜 필요했나

기존 trace 로그는 endpoint/root 메서드 중심이라 실제 Controller -> Service 흐름을 알 수 없었다. 로그가 찍히긴 하지만 요청 카운터 수준이었고, 엔진이 트리를 복원할 재료가 없었다.

### 반영 내용

- `MethodFrame`에 `callId`, `parentCallId` 추가.
- `CompletedNode` 신규 추가.
- `RuntimeTraceContext`가 `nextCallId`, `traceStartNanoTime`, completed node 목록을 관리.
- `RuntimeMethodBridge.exit()`에서 method pop 직후 completed node를 누적.
- `TraceLogSerializer`가 nodes 배열을 callId 오름차순으로 출력.

### 주요 파일

- `MethodFrame.java`
- `CompletedNode.java`
- `RuntimeTraceContext.java`
- `RuntimeMethodBridge.java`
- `TraceLogSerializer.java`

### 검증

- `..\gradlew.bat shadowJar` 성공.
- `.\gradlew.bat bootJar` 성공.
- `trace-202605031412.log`에서 `/board` 요청의 nodes 2개 확인.
  - node 1: `p=0`, BoardController
  - node 2: `p=1`, BoardService

## Unit 3 - try/catch 기반 exit 보장 계측

### 왜 필요했나

Unit 2에서 `error:true`를 붙이려 했지만, 하위 메서드 예외가 상위 프레임을 관통할 때 기존 `onMethodExit(ATHROW)` 방식으로는 상위 프레임 exit hook이 보장되지 않았다. 그 결과 에러 요청에서 trace가 닫히지 않는 문제가 생겼다.

### 반영 내용

- `MethodProbeAdviceAdapter`에 synthetic try/catch(Throwable) 블록 추가.
- 정상 return 경로는 `exit(methodId, false)` 호출.
- catch handler는 `exit(methodId, true/Throwable)` 호출 후 원래 예외를 재던짐.
- `onMethodExit(ATHROW)` 경로는 double-exit 방지를 위해 제거.
- catch handler에서 Throwable을 local 변수에 저장한 뒤 bridge 호출 후 다시 `ATHROW`.

### 주요 파일

- `MethodProbeAdviceAdapter.java`
- `RuntimeMethodBridge.java`

### 검증

- `..\gradlew.bat shadowJar` 성공.
- 에러 요청에서 trace 파일이 닫히고 `error:true`가 출력되는 것 확인.

## Unit 4 - 예외 메타데이터 추가

### 왜 필요했나

`error:true`만으로는 어떤 예외가 어디서 발생했는지 알 수 없었다. 에러 분석을 위해 최소한 exception class/message와 errorCallId가 필요했다.

### 반영 내용

- catch handler에서 Throwable을 bridge로 전달.
- `RuntimeMethodBridge.exit(int, Throwable)` 계열 추가.
- `RuntimeTraceContext`에 `errorCallId`, `exceptionClass`, `exceptionMessage` 추가.
- `errorCallId`는 최초 예외 발생 지점 기준 first-write-wins 처리.
- serializer에 compact/verbose 에러 필드 추가.

### 예시

```json
{
  "format": "trace",
  "endpointId": 149011136,
  "error": true,
  "errorCallId": 2,
  "exceptionClass": "org.springframework.dao.DataIntegrityViolationException",
  "exceptionMessage": "could not execute statement ..."
}
```

### 검증

- duplicate join 요청에서 `DataIntegrityViolationException` 출력 확인.
- `errorCallId`가 Controller가 아니라 Service 쪽 callId로 유지되는 것 확인.

## 서버 로그와 TurtlePick 로그 구분

- 서버 운영 로그는 애플리케이션/운영자가 관리하는 로그다.
- TurtlePick trace 로그는 `turtlepick.agent.logging.dir` 하위에 쌓이는 엔진 수거용 로그다.
- `logs/smoke` 하위 파일은 테스트 과정의 stdout/stderr 덤프이며, 서버 운영 로그도 엔진 수거 로그도 아니다.
- 엔진은 TurtlePick trace spool 경로에 대한 read/delete 권한을 가진다는 운영 전제로 간다.

## 남은 문제와 TODO

### TODO 1 - log-ready 실패 시 LOG_OFF

현재 log-ready 흐름은 파일 롤링 후 엔진에 `POST /api/agent/log-ready`를 보내는 구조까지 있다. 하지만 엔진 응답 실패 시 정책이 부족하다.

필요 정책:

- closed trace 파일에 대해 log-ready 전송.
- 응답 없거나 실패하면 1회 재시도.
- 재시도도 실패하면 서버 agent는 LOG_OFF로 전환.
- LOG_OFF 상태에서는 trace 로그 쓰기를 중단.
- 이미 닫힌 파일 삭제는 서버가 하지 않는다. 엔진이 spool 경로 권한으로 직접 읽고 삭제한다.
